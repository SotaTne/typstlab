# commit

コミットは、一つの論理的な変更と、その理由である。差分が変化で、メッセージが理由である。コミットは、ユーザーがコミットまたは分割を頼んだときだけ作る。メッセージだけを頼まれたときは、コミットせず文面を返す。push は頼まれたときだけ行う。

## 単位

一つのコミットは、一つの理由で件名が書ける範囲である。そのコミットだけを戻すと、その変更だけが戻る。

- 振る舞いを変える変更と、振る舞いを変えない整理は分ける。ユーザーが一度にコミットを頼んでも、理由が違う変更は別々のコミットにする。ユーザーが除いたファイルは入れない。それ以外の変更は捨てずに、対応するコミットへ入れる。
- その変更を固定するテストと、その変更で偽になる文書は同じコミットに入れる。ユーザーが分けると指定したときは、その指定に従う。
- 件名が一つの文にならないときは分割する。
- 各コミットのあとで、プロジェクトのビルドと、その変更が触れていないテストが通る。
- 仕様を期待値にした失敗するテストだけのコミットは、ユーザーがそれを頼んだときだけ作る。メッセージに、失敗することと、期待が仕様であることを書く。修正は入れない。

ステージはパスを指定する。秘密鍵（`*minisign*.key` など）、認証情報、依頼に無いファイル、追跡外の生成物（`target/`、`tmp/`、`.typstlab/` 配下のロックやキャッシュなど）は入れない。

## メッセージ

直近のマージ以外の件名の言語に合わせる。英語なら英語、日本語なら日本語。混在するときは数の多い方。

件名と本文のあいだに空行を置く。理由が件名だけで分かるときは本文を書かない。

件名は命令形である。目安は 50 文字、上限は 72 文字。言語で変えない。上限を超える説明は本文へ移し、件名を短くする。

- 英語は大文字で始め、ピリオドで終えない。検査は "If applied, this commit will <subject>" が自然な文になること。
- 日本語は辞書形にし、句点で終えない。検査は「このコミットを適用すると、<件名>」が自然な文になること。タ形にしない。

`feat:` や `fix:` などの接頭辞は、直近の履歴がそれを使っているとき、または `release-plz.toml` の changelog グループへ分類したいときだけ付ける。

本文は、変更前の問題と、この変更を選んだ理由を書く。差分の復唱と実装手順は書かない。72 文字で折る。段落のあいだは空行にする。

頼まれていない trailer は足さない。`Signed-off-by` も、リポジトリが要求するときだけ書く。問題番号は、ユーザーが示したときだけ、本文の末尾に `Resolves: #123` と書く。

## 手順

1. `git status`、対象の差分、直近の `git log` を見る。
2. 上の単位に分ける。
3. メッセージをファイルに書き、`git commit -F` で、指定したパスだけをコミットする。
4. `git status` で、入れたパスと残ったパスを確認する。

`git commit --amend` は、ユーザーが頼んだときだけ使う。push 済みのコミットは amend せず、新しいコミットにする。

## 例

件名:

```
ビルド出力先をフォーマット別のディレクトリへ分離する
```

失敗するテストだけの件名:

```
親ディレクトリ参照を含むテンプレートパスを拒否する失敗テストを足す
```

本文が要るとき:

```
PDF再ビルド時に他フォーマットの成果物が消えないようにする

PDF出力先が論文の成果物ルート直下になっていたため、再ビルド前の
ディレクトリ削除で配下のPNGやSVG出力まで一緒に消えていた。
```
