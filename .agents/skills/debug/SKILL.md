# Debug

再現しにくい不具合や症状ベースのバグを調査・修正するときはこの方針に従う。

## 原則

- 推測だけでコードを書き換えない。まず「どの境界・どのタイミングで壊れるか」を特定する。
- 修正の前に、その不具合を再現して失敗するテスト（Red）を書く。
- 1つの原因に対して最小限の修正を行い、既存のテストとビルドを壊さない。
- 同じ構造の弱点が周辺にないか確認し、必要なら同様にテストで固定する。

## 手順

1. **症状の言語化**: 何が起きるべきで、実際には何が起きているか（状態・出力・発生条件）を整理する。
2. **境界の洗い出し**: 関連する状態遷移・ファイルシステム境界・外部プロセス／通信境界を辿り、壊れうる仮説を列挙する。
3. **再現テストの作成 (Red)**: 仮説のうち再現可能なものを単体・結合テストとして書き、失敗することを確認する。
4. **最小修正 (Green)**: テストを通す最小限の修正を入れ、関連テストだけでなくワークスペース全体（`cargo test --workspace --all-targets`）を実行する。
5. **再発防止の点検**: 同種の状態漏れや競合が他にないか確認し、不要な一時ファイルや副作用を残さない。

## このプロジェクトで特に疑う境界

- **ファイルシステム・Store の原子的遷移とパス境界**: 同一ファイルシステム外（`/tmp` 跨ぎ）への `rename` 失敗、`stage` → `commit` / `backup` → `rollback` 間の競合や排他ロック漏れ、`..`・絶対パス・Windows ドライブプレフィックスによるパス脱出、成果物ディレクトリの親子衝突（`dist/<paper>/` と `dist/<paper>/png/` 等）。
- **外部ツール実行・ツールチェイン解決の境界**: キャッシュ済みバイナリの欠損やバージョン不一致（`VersionGuard` / `VersionProbe`）、OS・アーキテクチャ別アーカイブ展開（`tar.xz` / `zip` の `strip_components`・実行権限）、暗黙の `current_dir` や親環境変数（`TYPST_ROOT` 等）の混入、互換性 JSON（`resolver.json` / `typst_version_schema.json`）の定義ズレ。
- **CLI / MCP (`stdio`) とドキュメント・テンプレート変換の境界**: MCP `stdio` サーバーの stdout への意図しないログ混入による JSON-RPC 破損、プロジェクトルート指定時の相対パス解決ズレ、`.typstlab/typst_docs` 同期や `docs.json` → Markdown 変換のスキーマ差分、テンプレート `Value`（`Date` / `Array` 等）の TOML デシリアライズと Typst リテラル展開。
